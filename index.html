HR workflow automation

Cadence: four HR processes, one audit trail

Headcount reporting, performance check-ins, merit review and attrition risk usually live in separate spreadsheets owned by different people. Cadence runs them as one connected system with structured intake, automated routing and a full audit trail, so each workflow’s output feeds the next.

Compensation analytics

Comp Dash: market benchmarking on public BLS data

Pay benchmarks go stale in spreadsheets. Comp Dash pulls real Bureau of Labor Statistics wage data for five US metros, maps it to a fictional company’s job families, and flags where pay sits outside the market range. It is built for analysis and monitoring, not for setting pay.

  • Data pipeline
  • Market positioning
  • Pay equity monitoring

AI-assisted text analysis

Lens: open-text feedback, analyzed with guardrails

Survey comments and feedback pile up and get read once. Lens validates a batch, uses an AI model to score sentiment and pull out themes, stores every run so you can compare cycles, and keeps the paid model behind an admin gate and a model allowlist.

  • Responsible AI design
  • Trend over time
  • Governance controls

Workstream health

Meridian: status that is calculated, not declared

A status color updated on a Friday afternoon says whatever was last typed. Meridian calculates health from milestones, budget burn and open blockers, the same way for every workstream, with sign-in and row-level security so each person sees only their own data.

  • Scoring design
  • Role-based access
  • 35 written requirements

Process mining

IncidentOps: how work really flows

Averages hide the costly paths. IncidentOps applies process mining to a service-desk event log to show where real cases leave the intended process, which paths take longest, and where escalations bounce back and forth. It asks the same question I asked about inbound flow at Amazon: not who is slow, but where the order of the work breaks.

  • Process mining
  • Bottleneck analysis
  • KPI design

Method

How I build

Business analysis is how I work, not what I am. Every project follows the same four steps, and the documents are public so you can check the work.

  1. 01

    Start with the problem.

    Who is affected, what it costs, and what better looks like in numbers.

  2. 02

    Write the requirements.

    What the tool must do, what it must never do, what is in scope and what is out, and why.

  3. 03

    Build and document.

    The working tool, plus its process maps, data model and diagrams.

  4. 04

    Check it against the goal.

    Every feature traced back to a requirement, and every requirement back to an objective.
