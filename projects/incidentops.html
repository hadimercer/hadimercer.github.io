The Problem

A fictional mid-market enterprise IT service desk captures detailed event logs — ticket creation, assignments, escalations, resolution, closure, and customer feedback. But leadership relies on manual exports and surface-level averages, with no consistent view of how incidents actually flow end-to-end.

The primary failure mode is decision-making without process visibility. The same incident type can follow materially different paths (variants) with different cycle times, escalation patterns, and customer satisfaction outcomes. Without a process mining lens, teams cannot distinguish healthy flow from costly patterns like escalation ping-pong or premature closure.

Operational decision-making without process visibility means that improvement efforts target the wrong bottlenecks, escalation capacity is allocated by instinct rather than evidence, and the same quality failures recur cycle after cycle.

What It Does

  • Discovers and visualises the top process variants — how incidents actually travel through the service desk vs. the intended path, with frequency and cost weighting per variant
  • Quantifies step-level dwell time and waiting time to pinpoint true bottlenecks vs. active work time — the distinction between "long queue" and "slow work" is critical for the right intervention
  • Measures escalation and handoff churn — detecting ping-pong patterns (repeated back-and-forth reassignments) that consume L2/L3 specialist capacity without improving outcomes
  • Monitors closure governance — captures premature closures leading to reopens and correlates with customer satisfaction signals
  • Surfaces FCR (First Contact Resolution) proxy and enablement candidates — cohorts where low L1 resolution rate signals knowledge or training investment opportunities
  • Generates ranked problem candidates from repeat incident themes — volume, cycle time, and quality signals combined to feed problem management intake
  • Provides one-click CSV exports for high-value follow-up lists: ping-pong cases, closure exceptions, and enablement/problem backlogs

What This Demonstrates

  • Process mining thinking: going beyond averages to variant analysis, bottleneck quantification, and pattern distinction — the analytical approach a senior BA applies to process evidence
  • Requirements-driven delivery grounded in a formal product brief with five structured objectives, stakeholder archetypes, and full scope definition with constraints documented
  • Analytics-only scope explicitly bounded — no ticket actions, no live ITSM integration — with rationale documented (descriptive analytics vs. operational system scope)
  • PostgreSQL schema design and analytical view modelling for process mining metrics — business logic lives in SQL views, keeping the UI thin and the analytical contracts explicit
  • Operational thinking: outputs designed for three distinct stakeholder audiences — Process Owner, Operations Manager, and Quality/CX Lead — each with different analytical needs
  • Idempotent data engineering: CSV ingestion with canonical event mapping, event key hashing for duplicate protection, and repeatable load behaviour

BA Process

Problem Framing

The starting point was a specific failure mode observed across IT service desk operations: teams know their aggregate metrics (average cycle time, total ticket volume, SLA percentage) but cannot explain why those metrics are what they are. The analytical gap is between the number and the pattern. Process mining addresses this by treating the event log as a structured process record rather than a transaction log.

Scope Constraints

ConstraintRationale
CSV input only — no live ITSM integrationLive integration requires API access, authentication, and data contract agreements with the source ITSM platform — disproportionate for an analytics demonstration
Analytics-only — no ticket actionsWriting back to the ITSM system introduces operational risk; the product is a decision-support tool, not an operational system
Descriptive outputs — not causal proofCorrelation between process patterns and outcomes is presented as evidence for investigation, not as causal determination
SLA compliance is policy-basedSLA targets are configured, not sourced from an authoritative ITSM flag — keeps the tool independent of any specific platform's SLA definition

Design Decisions

Business logic lives primarily in SQL analytical views rather than in the Streamlit application code. This keeps the UI thin, makes the analytical contracts explicit and auditable, and allows the dashboard to change without touching the underlying metric definitions. Each workstream queries a defined view — the view is the contract.

Idempotent loading was treated as a non-negotiable requirement from the start. The event_key hash computed per row ensures that re-loading the same CSV produces no duplicate records — a critical property for a tool that will be run repeatedly across review cycles.
