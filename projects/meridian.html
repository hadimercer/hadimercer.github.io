The Problem

Project managers have Jira and Asana. But business analysts, consultants, finance managers, and HR leads who manage work as a by-product of doing their job don't think of themselves as project managers — those tools are alienating and abandoned within weeks.

The fallback is a spreadsheet with a RAG column updated when there's time on a Friday afternoon. That spreadsheet doesn't alert when a workstream is drifting. It shows whatever was last typed.

Meridian's central design principle: health status is calculated, not declared. A user never selects a RAG colour. They enter objective data — milestone completions, spend figures, open blockers — and Meridian calculates what the data means. A 9-question context wizard at workstream creation tunes the scoring engine so a hard-deadline client engagement is scored differently from a self-imposed internal initiative.

What It Does

  • Calculates composite RAG from three weighted dimensions: Schedule Health (milestone pace vs. elapsed time), Budget Health (planned vs. actual burn), and Blocker Health (unresolved blocker age)
  • 9-question context wizard at setup tunes scoring thresholds — 15 modifier rules document every combination and its effect on the three health dimensions
  • Multi-user collaboration with role-based access (Owner / Contributor / Viewer), invite link system, and per-entity comment threads
  • Staleness flag fires when update cadence exceeds the configured threshold — the system alerts the user when their own data has gone stale
  • Portfolio analytics: health trend over 30 days, schedule vs. budget scatter matrix, milestone velocity table, blocker age analysis
  • Six-page workstream view: Overview, Milestones, Budget, Blockers, Updates (typed post feed), Team management

What This Demonstrates

  • Full product thinking: problem statement, stakeholder personas, scoping decisions, and design rationale all documented before a line of code was written
  • 35-requirement BABOK-aligned FRD with MoSCoW prioritisation, stakeholder objectives, and full traceability matrix
  • Scoring engine designed as a requirements problem first — the modifier matrix in the FRD precedes the code in pipeline/scoring.py
  • PostgreSQL schema with 15+ tables, FK constraints, and row-level security via Supabase — no user can read another user's workstream data without explicit invitation
  • Auth and security: Supabase Auth, RLS on all user-scoped tables, zero credentials in source code (NFR-02b)
  • UML class diagram documenting the full data model (FR-34); BPMN covering workstream lifecycle and invite sub-process (FR-35)

RAG Scoring Engine

The scoring engine is Meridian's core differentiator. RAG status is never a manually selectable field — it is recalculated from source data on every relevant change. Three health dimensions feed a weighted composite score.

Schedule Health

Formula
SV = Milestone Completion % − Time Elapsed % Green: SV ≥ −10% (on track) Amber: −25% ≤ SV < −10% (lagging) Red: SV < −25% (at risk)

Budget Health

Formula
BV = (Planned Spend to Date − Actual Spend) / Total Budget Green: BV ≥ −5% (on budget) Amber: −15% ≤ BV < −5% (over plan) Red: BV < −15% (budget at risk)

Blocker Health

State Score Default Status
No open blockers100Green
1 blocker, < 3 days80Green
1 blocker, 3–7 days55Amber
1 blocker, > 7 days25Red
2+ blockers (any age)40 maxAmber+

Composite Score

Weighted Average
Composite = (Schedule × 0.40) + (Budget × 0.35) + (Blockers × 0.25) Green ≥ 70 | Amber 40–69 | Red < 40

Wizard Modifier Examples

Wizard Answer Effect on Scoring Thresholds
Hard / contractual deadlineSchedule Amber tightens: −10% → −5%; Red: −25% → −15%
Client-billable budgetBudget weight increases 35% → 45%; Amber at −3%, Red at −10%
Blocked by external partyBlocker age thresholds halved — risk accumulates faster
High / Critical risk ratingAmber-to-Red band compressed 5–10% across all dimensions
Review / Closing phaseAny incomplete milestone > 2 days past due triggers Amber

BA Process

1. Problem Discovery → Target User Definition

The problem statement did not start as a feature list. It started with a single observation: professionals who manage parallel workstreams abandon structured tools quickly, then revert to spreadsheets with manually updated RAG columns. The core question was not "what should the tool do?" but "why do existing tools fail this user?"

Three stakeholder archetypes were defined before any functional requirements were written:

  • The Independent Operator — a BA or consultant managing 3–5 concurrent engagements with no team, primarily needs a personal health signal and an honest prompt to act. Drove the staleness flag (FR-10)
  • The Team Lead — manages a cross-functional team, needs to delegate data entry and control role-based visibility. Drove the invite-link flow (FR-03, FR-30) and role system (FR-29)
  • The Executive Reviewer — no data entry, needs a single-screen portfolio view and will disengage immediately if the tool requires any learning curve. Drove the Viewer role (FR-28, FR-30)

2. Scoring Engine as a Requirements Problem

The most consequential design decision was treating the scoring engine as a requirements problem before a technical one. Letting users set their own RAG colour was explicitly rejected in the FRD — it reproduces the exact failure mode of the spreadsheet. The modifier matrix documents every wizard combination and its downstream effect on scoring thresholds, and was written before the first line of scoring.py was produced.
