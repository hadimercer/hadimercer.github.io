The Problem

Teams regularly collect large volumes of qualitative text — customer comments, engagement survey responses, support notes, incident narratives, implementation feedback — but the analysis workflow breaks down in one of three places: the incoming text is messy, the interpretation lacks business context, or the results aren't stored in a way that supports historical comparison.

Lens treats text analysis as an operational workflow, not a one-off prompt. Analysts validate a batch, attach business context, compare it against prior cycles, persist the run, and reopen it later without re-calling the model. The second design problem Lens addresses is governance: a public app that can call a paid API needs controls. Lens separates public review access from live execution through runtime mode detection, admin gating, and explicit model selection controls.

What It Does

  • Accepts CSV uploads or pasted text, runs UTF-8 validation, detects text columns and timestamps, enforces batch limits, and gates execution behind a 5-row preview confirmation — no model calls until the analyst confirms the batch
  • Runs an OpenAI-backed pipeline: record-level sentiment scoring, theme extraction, executive summary generation, and anomaly detection — with retry handling on malformed model output
  • Supports named longitudinal series — retrieves the most recent prior cycle and injects that context into each new run so the model's summary is aware of what changed since last time
  • Persists all results to PostgreSQL: analysis runs, normalised batch records, context profiles, pipeline run log — results are queryable and durable
  • Runs in Demo Mode when no API key is present — seeded historical analyses load from the database so the app is fully reviewable without live execution
  • Gates live execution behind an admin password on the New Analysis page — public users can browse the Analysis Library without triggering any API cost

What This Demonstrates

  • LLM workflow design: sentiment scoring, theme extraction, structured summary generation, retry handling — treating the model as a component in a pipeline, not a chat interface
  • Data validation and ingestion engineering: text-column detection, timestamp detection, empty-row rejection, preview gating, and batch size enforcement before any API call is made
  • Longitudinal analysis design: named series, prior-cycle retrieval, run sequencing, and historical comparison context — qualitative data treated as a repeatable operational workflow
  • Five-table PostgreSQL schema with FK chains, helper functions, indexes, and idempotent bootstrap logic — schema and seed data run automatically on first deploy
  • Governance for public AI demos: Demo/Live mode split, admin password gate, model allowlist, safe public browsing without API exposure
  • BA artifact depth: FRD, Data Flow Diagram, Entity Relationship Diagram, Use Case Diagram, schema SQL, and seed SQL — six distinct artifacts covering requirements, data, and system boundaries

Pipeline Architecture

Six sequential stages from source text to stored results. Each stage has defined inputs, outputs, and failure modes documented in the DFD artifact.

1
Ingestion & Validation
UTF-8 validation, text-column detection, timestamp detection, empty-row rejection, 5-row preview generation, batch size enforcement
2
Context & Series Resolution
Analyst adds batch label, domain tag, and optional context profile. If a series name is supplied, prior-cycle run is retrieved and injected as context
3
Admin Gate & Confirmation
In Live Mode, execution requires admin password unlock. API footprint is displayed before confirmation. In Demo Mode this stage is skipped
4
OpenAI Pipeline Execution
Record-level sentiment scoring → theme extraction → structured summary generation → key takeaways + priority actions → anomaly detection. Retry on malformed output
5
Persistence
Upsert series registry, assign run_sequence, persist analysis_results + normalised batch_records + context_profiles + pipeline_run_log. Runtime migration guard runs here
6
Dashboard Render & Historical Review
Executive summary, ordered takeaways, priority actions, sentiment split, theme heatmap, anomaly flags, optional sentiment-over-time view, prior-cycle comparison

Database Schema

Five-table PostgreSQL schema. FK chains enforce the relationship between series, runs, and records. Idempotent bootstrap applies schema and loads seed data on first deploy without manual intervention.

series_indexNamed longitudinal series registry — groups related runs togetherseries_name, created_at, run_count

batch_recordsNormalised individual records per run — one row per text unit with per-record sentiment scorerun_id, record_index, text_content, sentiment_score, sentiment_label

BA Process

Problem Framing

The problem was framed around three specific failure modes in qualitative analysis workflows: messy input, missing business context, and no historical record. Each failure mode drove a specific design requirement — validation gates for the first, context profiles for the second, named longitudinal series and persistent storage for the third.

The secondary problem — governance for a public demo — was treated as a first-class design requirement rather than a deployment afterthought. Demo Mode and the admin password gate were specified in the FRD before the first line of code was written.

Design Decisions

DecisionRationale
PostgreSQL as system of record (not session state)Analysis results must be durable and queryable independently of the session. A reviewer should be able to close the tab and reopen the same analysis days later without re-running the model
Demo Mode as a first-class pathThe app must be reviewable without an API key. Seed data bootstrapped on first deploy means the app is immediately useful to any portfolio reviewer regardless of credentials
Short-lived psycopg2 connectionsSupabase free tier drops idle sessions. Per-request connection factory avoids connection pool exhaustion on a long-lived Streamlit session
Prior-cycle context injected at model call timeThe model's summary is meaningfully different when it knows what was observed in the prior cycle. This requires retrieving and formatting the prior run before the API call, not after
Retry on malformed model outputLLM output is probabilistically structured. A retry on parse failure — without re-calling for valid records — is cheaper than failing the whole batch

Scope Decisions

Excluded FeatureRationaleFuture Phase
Multi-user accounts / authSingle-analyst workflow for v1; admin password gate provides sufficient access control for portfolio demonstration without auth infrastructurePhase 2
Real-time streaming analysisBatch processing is the right fit for the stated problem (survey cycles, support batches) — streaming adds infrastructure complexity without changing the analytical modelPhase 3
Custom model fine-tuningPrompted base models are sufficient for the accuracy level required in business text analysis; fine-tuning requires labelled training data not available for synthetic demonstrationsPhase 3
