IncidentOps: System Architecture

Four-layer analytics pipeline converting incident event logs into structured process mining insights and operational dashboards.

01Overview

IncidentOps PMI Hub implements a four-stage analytics pipeline. A semicolon-delimited incident event log is exported from a source ticketing system, ingested via a Python loader, transformed into analytical views via SQL, and surfaced as process mining insights through a six-workstream Streamlit dashboard.

The design deliberately prioritizes reproducibility and portfolio readability over complex infrastructure. Business logic lives primarily in SQL views, which keeps the UI thinner and easier to explain in stakeholder handoff contexts.

CSV Export (source ticketing system)
↓ load_csv.py: validate · normalize · idempotent event keys
PostgreSQL (raw storage + canonical event mapping)
↓ SQL analytical views: process mining calculations
Streamlit Dashboard (6 workstream modules)
↓ read-only analytics: no ticket mutation
End User (service owners · ops managers · team leads)

02Architecture Layers

LayerComponentResponsibilityDesign Decision
Ingestion load_csv.py Maps source columns, validates timestamps, computes idempotent event keys, stages data to PostgreSQL Idempotent keys prevent duplicate event rows on re-import. Validated at ingestion boundary, not at query time.
Storage PostgreSQL (raw + views) Separate raw storage from canonical event mapping and analytical views. All business logic lives in SQL, not the application layer. SQL views mean any BI tool or analyst can reproduce the calculations independently of the Streamlit UI.
Presentation Streamlit (6 workstreams) Queries analytical views; surfaces process mining metrics, KPIs, and variant analysis through interactive dashboard modules. Shared theme layer supports reusable components across workstreams. UI is thin: pure consumer of SQL view output.
Testing Test suite Covers loader normalization, SQL object structure, and app query contracts. Optional DB-backed tests via TEST_DATABASE_URL. Test scope is deliberately limited to what's verifiable without a production environment, appropriate for a portfolio context.

03Dashboard Workstreams

The Streamlit dashboard is organized into six operational workstreams, each addressing a distinct analytical lens on the incident process:

Command Center

Portfolio-level KPIs and executive summary metrics. Entry point for service owners reviewing overall incident health across the period.

Flow

Cycle time distributions, variant analysis, and process path frequency. Surfaces which incident routes are most common and where time accumulates.

Handoffs

Inter-team transition analysis. Identifies routing friction, excessive handoff chains, and team-to-team dwell times.

Quality

Escalation churn, reopen rates, closure compliance, and FCR (First Contact Resolution) analysis by category and team.

Intake

Incident intake pattern analysis: volume by channel, category, time of day, and priority. Supports demand forecasting discussions.

Enablement

Team-level performance and capacity analysis. Surfaces workload distribution and identifies enablement opportunities.

04Deployment & Configuration

Database Connectivity

Two connection strings are used: DATABASE_URL_DIRECT for bootstrapping (schema creation, initial seed) and DATABASE_URL_POOLED as the application's preferred runtime connection. Configuration is managed via environment variables, with no credentials in code.

Deployment Target

Designed for Streamlit Community Cloud (free tier) for portfolio purposes. Local execution via streamlit run app.py with a .env file is the primary development path. The architecture requires no message queues, background workers, or external caching services.

Design Scope Boundary

This is an analytics tool: it does not update tickets and relies on CSV input rather than live integrations. The system assumes event timestamps are sequentially reliable and treats reopens as meaningful quality signals. Process mining outputs are descriptive, not causal proof.
