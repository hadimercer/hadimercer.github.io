01 Purpose & Context

This document defines the functional and non-functional requirements for Meridian, a full-stack multi-user SaaS application for workstream portfolio health tracking. It is produced as a BABOK v3-aligned BA artifact and serves as the primary requirements baseline for the build, test, and documentation phases of the project.

Meridian addresses a specific failure mode: professionals who manage concurrent workstreams — business analysts, consultants, finance managers, HR leads — abandon structured project management tools (Jira, Asana) because those tools are designed for people who identify as project managers. The fallback is a spreadsheet with a manually updated RAG column. That spreadsheet cannot alert when a workstream is drifting; it shows whatever was last typed.

Meridian's central design principle: health status is calculated, not declared. A 9-question context wizard tunes the scoring engine per workstream — a hard-deadline client engagement is scored differently from a self-imposed internal initiative. Requirements FR-07 through FR-10 define this engine in full.

06 Non-Functional Requirements

NFR-01a — Data Integrity: Staleness Tracking
Score history shall be preserved as an immutable audit trail
Every calculated composite score shall be written to rag_score_history as a timestamped snapshot. Scores shall not be updated in place; each recalculation produces a new row. This preserves the full trend history visible on the Analytics page and prevents retroactive modification of health status records.
Rationale: The trend line on the Analytics page is the primary evidence that a workstream's health moved over time. If scores were updated in place, the historical narrative would be lost and the analytics surface would be meaningless.
NFR-01b — Data Integrity: Audit Trail
Wizard configuration changes shall be logged with before/after state
When an Owner re-runs the context wizard (FR-06), the previous wizard configuration shall be preserved in a change log with timestamp and the identity of the user who made the change. The current active configuration is always the most recent record.
Rationale: Wizard answers directly control scoring thresholds. A change to the wizard mid-workstream will change RAG status even without any change to milestone, budget, or blocker data. The audit trail makes this visible and prevents silent threshold changes.
NFR-02a — Security: Row-Level Security
All workstream data shall be isolated at the database layer
Row-level security (RLS) policies shall be applied to all user-scoped tables in Supabase. No authenticated user shall be able to read, write, or delete data belonging to a workstream they have not been explicitly invited to, regardless of how the application layer is accessed. RLS shall be enforced even if the Streamlit application layer is bypassed.
Rationale: Application-layer access control alone is insufficient for a multi-user system handling professional workstream data. Database-level enforcement prevents any misconfiguration in the Streamlit layer from exposing cross-user data.
NFR-02b — Security: Credential Management
No credentials shall appear in source code or version control
All secrets (database host, password, Supabase URL, anon key) shall be managed via environment variables loaded from .env locally and Streamlit Cloud secrets in deployment. The .env file shall be listed in .gitignore. No hardcoded credentials shall appear anywhere in the repository.
Rationale: Publicly accessible GitHub repository. Any hardcoded credential would be immediately and permanently compromised.
NFR-03 — Performance: Database Connection
Database connections shall use the Supabase transaction-mode pooler
All PostgreSQL connections shall use the Supabase pooler endpoint on port 6543 rather than a direct connection on port 5432. The pooler username format shall be postgres.{project-ref}. Read queries shall use @st.cache_data(ttl=300) and cache shall be cleared immediately after any write operation.
Rationale: Streamlit Cloud's serverless execution model cannot hold long-lived direct PostgreSQL connections. Direct connections fail intermittently in this environment. The pooler is the only reliable connection mode for Supabase on Streamlit Cloud.
NFR-04 — Usability: Cold Start Transparency
Cold start delay shall be documented in the README
Streamlit Community Cloud on the free tier may take up to 30 seconds to initialise after a period of inactivity. This delay shall be documented in the repository README so that portfolio reviewers are not misled into thinking the application is broken.
Rationale: Portfolio reviewers encountering a 30-second blank screen without explanation will form a negative impression of the application's reliability. Transparent documentation prevents this misattribution.
